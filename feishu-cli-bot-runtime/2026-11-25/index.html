CLI Bot 身份能否替代现有 IM Feishu 连接

结论：可以有条件替代，但不能一键替换。lark-cli --as bot 在能力面可以覆盖现有 IM Feishu 的消息入口、消息出口和主 Agent 的飞书工具调用；但 Cloud 的连接、群绑定、线程、审批、附件、去重、outbox 与 durable delivery 必须保留并重新接线。当前证据只到本机命令级，尚未完成真实企业端到端验证。决策是：批准作为替换方案进入 UAT 和灰度，不批准立即删除旧 IM Feishu 链路。

一、可行性判断

能替代的理由。CLI 已具备 Bot 身份下的消息事件、卡片事件、IM 发送、Wiki 只读、文档、云盘、通讯录、任务等能力；本机隔离验证已确认 im.message.receive_v1、card.action.trigger 的 auth_types 为 bot，IM 与 Wiki 命令接受 --as bot。身份上仍是同一个 Bot 应用的 tenant token，不需要用户 OAuth 或个人 UAT；企业内嵌还可用 Go extension 接中心化凭据、命令白名单和审计。因此“用 CLI 的 Bot 身份作为唯一飞书接入层”在技术上成立。

不能直接替换的理由。CLI 是子进程和命令协议，不是原有进程内 WSClient。生产替换必须新增事件消费者管理器、租约、ready marker、NDJSON 解析、stdout 完整性、重连、版本固定、多实例防重复、命令治理和可观测性；还要保持 same-card working/final/error、AskUserQuestion、审批幂等、附件、线程与投递状态。全部应用权限也只是上限，真实 tenant scope、事件订阅、机器人能力、已发布版本、群/知识空间/文档 ACL 仍要核对。

结论。这是“替换消息通道＋工具执行层”的独立工程，不是换一次认证。若 P0 只是让知识库可用，不需要替换整套 IM 连接，保留现有 Bot 并新增知识库资料源更稳；若目标是把主 Agent 做成飞书内的完整工作入口，则 CLI Bot 替换方案可行，应进入真实应用 UAT 与灰度。

二、与当前方案的区别

当前方案是继续由现有 IM Feishu 连接使用官方 SDK WSClient 收事件，Cloud 保存连接与状态，renderer 通过 SDK 发消息、卡片和附件；知识库作为新增只读资料源接给主 Agent。变化集中在新资料源，不改变消息 runtime。

替换方案是用 CLI Bot Runtime 接管入站事件、出站消息和飞书 API 调用：CLI 事件消费者替换 WSClient，CLI adapter 替换 IM/CardKit 的 SDK 调用，工具网关把 IM、Wiki、Docx、Drive、Contact、Approval、Task 等 Bot 受权能力统一提供给主 Agent。App ID/Secret、tenant token、Cloud 连接与群绑定、Agent 会话仍然保留，改变的是这些能力如何被接收、调用和运维。

实际差异不在用户看到的群聊或私聊，而在进程模型、能力面、凭据投影、可靠性、性能和发布方式：从进程内 SDK 变成常驻事件消费者与短命令子进程；从单一 IM 能力面扩大到完整 CLI 业务域；从 Cloud 直接持有 SDK 连接变成按 connection 维护 profile、消费者和租约；从现有监控变成还要监控 CLI 健康、事件丢失、命令延迟和审计。

这张图说明了替代方案的主线：用户在原群聊、私聊和卡片上发起任务；飞书开放平台把事件与能力资源交给 CLI Bot Runtime；Cloud 继续拥有连接与业务状态；主 Agent 通过工具网关访问 Bot 被授权的能力；最终回复仍由 IM 与卡片链路回到用户，保留 working、final、error、附件和审批动作。

三、影响范围与最终判断

  1. 必须改：事件入口、消息与卡片出口、附件、飞书 SDK 调用、凭据运行时投影、CLI 二进制与版本、profile 生命周期、消费者管理器、租约、监控告警和回归测试。
  2. 必须保留：用户连接、群绑定、线程映射、事件去重、审批 intent、outbox、delivery lease、durable WSS delivery、same-card 状态机、AskUserQuestion 和主 Agent 会话语义。
  3. 新增治理：强制 --as bot、中心化凭据、命令白名单、资源 ACL、写操作确认、统一审计、输出大小限制、限频退避与正文按需读取。
  4. 验证范围：真实应用配置、群消息、私聊、卡片按钮、审批幂等、附件、断线重连、事件去重、知识库召回、权限撤销、性能与数据流、多实例租约和回滚演练。

影响范围结论：高风险集中在 IM Gateway、renderer、Cloud 状态接线和发布运维；中风险在主 Agent 的完整飞书工具面与知识库数据流；用户会话语义和 Cloud 业务状态本身不应被重写。任何一项等价回归失败，都不能删除旧通道。

最终判断：可以替代，但当前只能批准进入真实验证，不能宣布已完成替代。推荐按“真实应用 UAT → 入站影子消费 → 单群灰度 → 主 Agent 工具逐域开放 → 按 connection 切换 → 退旧通道”执行；全过程保留旧 IM Feishu 连接作为回滚路径。只有全部验收通过后，才允许把 CLI Bot Runtime 作为唯一飞书接入层。若验收不通过，则保留现有连接，仅以独立知识库和工具方式交付本期需求。

证据边界：官方 lark-cli v1.0.100 的本机命令级验证已经完成；真实企业应用配置、事件送达、知识库正文召回、生产等价性与稳定性尚未验证。help、schema 与 --dry-run 不能算端到端结论。
