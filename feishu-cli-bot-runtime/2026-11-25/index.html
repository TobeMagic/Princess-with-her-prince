技术方案结论 · 2026-11-26

用 CLI Bot 替换旧应用注册，并把 CLI Skills 接入主 Agent

结论：可以。目标就是换掉原来的 Bot 应用/注册入口，不用另造一套 Bot Runtime。lark-cli config init --new 创建的全权限 Bot 应用提供新的 appId/appSecret；把这对凭据导入现有 Cloud credentialRef，原来的 WSClient、IM Gateway、群绑定、卡片、审批和 durable delivery 继续工作。CLI 的 --as bot 命令和 Skills 则作为主 Agent 的飞书工具接入，复用同一个应用身份。前提是真实应用配置与权限已发布，并完成连接迁移和真实企业 UAT。

一、到底替换什么

替换的是旧 Bot 应用与 app registration 认证入口。此前调研已经核对：CLI 的 config init --new 通过 PersonalAgent 应用注册返回 client_id/client_secret；Cloud 的 import-app-registration 需要的也是 App ID/Secret、Bot open id、扫码用户、tenant 和 scopes。把新应用返回的凭据与 Bot identity 导入 Cloud 后，现有 runtime 就能继续用 App ID/Secret 建 WSClient，消息入口和回复出口无需改成 CLI 子进程。

这里不需要“把旧消息链路改写成 CLI 消费者”，也不需要新建 Bot Runtime。CLI 在这里有两类用途：一是产出并绑定新的 Bot 应用，二是把它的命令能力和 Skills 交给主 Agent。旧链路里已经解决的群绑定、线程映射、事件去重、same-card、审批幂等、附件、outbox 和 durable delivery 继续留在 Cloud/Desktop，不动业务状态。

CLI 与 Skills 的接入方式是把同一个 App ID/Secret 绑定给 Agent 运行环境，配置 bot-only 身份；主 Agent 获得 lark-wiki、lark-doc、lark-drive、lark-im、lark-event 等 Skills，以及 wiki、docs、im、contact、task、base、sheets 等 Bot 身份命令。工具调用统一带 --as bot，不引入用户 OAuth 或个人 UAT。企业内嵌时通过 Credential、Restrict、Observer 接服务端凭据、命令白名单和审计。

二、与旧链路的关系

控制面：管理员用 CLI 创建并获得全权限 Bot 应用的 App ID/Secret；核对 6 项 IM tenant scope、消息/卡片事件、机器人能力、知识库只读 tenant scope、版本发布和资源 ACL。把应用凭据与 Bot open id 导入 Cloud，替换旧 credentialRef 指向的应用。

消息面：用户在原群聊、私聊和卡片上继续工作。事件仍由现有 WSClient 收入，Cloud 继续处理连接、去重、线程、审批与 delivery；回复仍由现有 renderer 发文本、卡片和附件。用户感知是同一个 Bot 在群里，只是背后的应用身份换成新的全权限 Bot。

能力面：主 Agent 在任务执行过程中调用 CLI Skills：搜知识库、读文档、查云盘、发消息、查通讯录、创建任务、处理审批等。工具结果带引用、资源 ID 和错误分类，不把整库正文无边界塞进上下文；写操作按工具策略确认并审计。

与“CLI 全量重写消息链路”的区别：全量重写会把 WSClient、IM SDK 调用和卡片回写都换成 CLI 消费者，随之要重建进程生命周期、租约、NDJSON 解析和多实例去重。本方案不采用这条路径；它只替换应用注册与凭据，把能力扩到主 Agent。这样改动面更小，原有消息可靠性语义不丢。

三、影响范围与结论

  1. 要改：Settings/后端的 app registration 入口；Cloud 的新应用凭据导入、旧连接迁移和 open_id/Bot open id 映射；应用身份 scope 与事件 readiness；主 Agent 的 CLI Skills 安装、凭据绑定、工具白名单与审计。
  2. 保留：WSClient 消息入口、Cloud 连接、群绑定、线程、卡片、审批、附件、事件去重、outbox、durable delivery、same-card 状态机和告警。
  3. 新增：主 Agent 的 Bot 身份能力面；知识库/文档/云盘/通讯录/任务等 Skills；按 connection 选择 Bot profile；写操作确认、资源 ACL 与结果大小控制。
  4. 验证：真实应用版本元数据、群消息、私聊、卡片、审批、附件、知识库召回、撤权、断线重连、主 Agent 调用链路、性能和回滚。

影响范围结论：改动集中在新应用注册/凭据迁移、权限核对和主 Agent 工具接入；消息 runtime 与 Cloud 业务状态保持不变。风险主要是换 App 后的用户标识与绑定兼容、全权限应用的实际 tenant scope、Bot 资源 ACL，以及 Skills 的写操作边界。

最终判断：这个方案可以替代旧的 Bot 应用注册，是当前更合理的主方案。条件是用真实企业应用核对并发布所需 tenant scope、事件和机器人能力，完成旧连接到新应用的迁移，再把 CLI Skills 以 Bot 身份接入主 Agent 并通过端到端 UAT。无需另造 Bot Runtime，也无需把现有 IM Feishu 链路重写成 CLI 子进程。若真实应用验证失败，才回退到“保留旧应用，仅新增知识库能力”。

证据边界：本机已验证 CLI v1.0.100 的 Bot 事件、IM、Wiki 命令和 Skills/命令面；尚未执行真实企业应用授权、事件送达、知识库正文召回或线上切换。截图中的 171 项权限不能替代对已发布应用版本 token_types 与 event_infos 的核对。
