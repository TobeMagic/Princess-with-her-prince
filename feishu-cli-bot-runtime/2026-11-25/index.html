产品定义与验收愿景

主 Agent 是飞书中的工作伙伴：收到消息后，能在授权范围内找资料、理解内容、完成工作，并以用户熟悉的飞书消息和卡片返回结果。

目标

  • 用一个明确的 Bot 身份承接飞书消息入口与主 Agent 的飞书工具调用。
  • 替换原 Bot 消息通道的实现时，延续群聊、私聊、卡片、审批、附件和会话连续性。
  • 让主 Agent 在 Bot 的应用身份权限和资源授权范围内，使用消息、知识库、文档、云盘、通讯录、任务等飞书能力。
  • 权限、可见范围、操作结果和失败原因可被用户理解，可被运营与研发追溯。

非目标

  • 不承诺 Bot 能读取所有企业资源，更不承诺访问用户个人资源。
  • 不在本轮定义用户 OAuth、个人身份模拟或个人 token 管理。
  • 不在评审稿中写死技术蓝图、具体命令映射或数据库字段。
  • 不因“全量权限”默认开放高风险写操作；实际产品入口仍需明确确认与审计。
  • 不把本机命令验证当成真实企业链路已验收。
待评审结论：是否接受“替换通道、延续产品体验、逐步开放能力”作为统一目标？如果接受，后续才进入具体技术方案与排期；如果不接受，需要先明确是仅接知识库，还是替换整个 Bot 消息通道。

用户体验：工作留在飞书里

用户不需要知道 Bot 身份背后用了哪种工具。他只需在群或私聊里提出任务，主 Agent 负责在可见的飞书资源中完成，并说明结果或阻碍。

知识库的 P0 用户价值用户问一个只有内部知识库能回答的问题，Bot 给出答案、文档标题与可打开的引用。没有访问权时，明确说明需要谁授权。
发起任务群聊、私聊、卡片动作
→
主 Agent 工作在 Bot 授权范围内检索、理解、执行
→
飞书内交付答案、引用、状态与下一步
群成员

在一个项目群里，直接问到知识库里的答案

期望：Bot 理解群上下文，在已授权资料中找答案；答案有出处；资料无权限或不存在时不说“查无此资料”来掩盖权限问题。

知识管理员

只把指定空间交给主 Agent，而不是交出整个飞书账号

期望：管理员能理解 Bot 可见哪些空间，能撤销授权；用户的实际可见范围由应用权限和资源 ACL 共同决定。

审批参与者

原来的卡片、按钮和追问仍然可用

期望：替换通道后，进行中的工作、最终结果、错误状态和审批反馈保持一致；重复点击不重复执行。

产品运营

看到飞书能力可用，也能看到失败和修复入口

期望：连接、权限不足、Bot 未加入资源、任务执行失败分别可诊断；撤销或断开连接后不再返回旧资料。

主 Agent 的能力范围

“全部权限”是应用身份可被授予的能力上限，不是用户天然能访问一切。每一项能力都需要应用身份权限、已发布配置和具体资源授权，且要有明确的产品边界。

消息与协作

群聊、私聊、回复、卡片状态、附件与审批动作。替换通道的第一条验收底线：现有交互不能因接入方式改变而退化。

必须评审：既有体验等价

知识库与文档

发现授权空间、找到候选文档、读取正文、给主 Agent 提供上下文，并在回答中保留标题与引用链接。

P0：先明确可读范围

云盘与附件

在 Bot 被授权的范围内发现、读取或下载资料；为工作流提供文件入口，不扩展到用户私人云盘。

后续能力：逐域开放

通讯录与任务

辅助识别人、群和工作对象，让主 Agent 能在授权范围内完成协作任务。涉及写入或外发时要有确认和结果反馈。

后续能力：确认操作边界
关于 171 项权限的正确产品表达截图中的“全部权限 / 已选 171 项”不能单独证明每项都属于 Bot 身份，也不能证明事件、机器人能力、版本发布或空间访问已生效。评审应以真实应用的身份权限和资源授权为准。

产品与技术共同评审什么

技术实现可以后续选择，但下面这些产品约束必须先对齐。它们决定主 Agent 是不是一个可长期使用的企业工作入口。

评审主题要确认的问题产品对齐标准
身份与凭据复用现有应用还是新建应用？谁负责开通、发布与撤销？主 Agent 始终使用明确的 Bot 应用身份；用户不会误解为个人授权。
可见范围哪些群、空间和文档可访问？按用户、群还是工作区约束？Bot 的授权范围可查看、可解释、可撤销；不同用户的可见范围不越界。
消息与会话群聊、私聊、线程、卡片、审批、附件怎样延续？原有工作不因替换通道而丢失；消息和审批不重复处理。
主 Agent 工具哪些能力默认可用？哪些要确认？按用户任务逐步开放；不把“应用有权限”直接变成“任意操作都自动执行”。
状态与反馈工作中、成功、失败、权限不足、资源缺失如何表达？用户知道任务是否完成；管理员知道缺哪项权限或资源授权。
稳定性断线、重启、重连、连接撤销时如何表现？不静默丢消息、不重复执行；有健康状态和故障恢复目标。
性能与数据流知识库如何召回？正文何时读取？列表与正文按需读取；有分页、限频和引用要求；不把整库无边界塞入主 Agent。
发布与回滚如何灰度替换？旧通道何时退出？先验证等价，再逐步切换；保留回滚条件，不在验证前删除旧通道。

本轮需要产品确认的 8 个决策

没有这些确认，研发只能各自补假设。建议在评审会后逐项落定，不需要在此刻选择技术实现。

  1. 接入范围：只接知识库，还是替换整个 Bot 消息通道？

    本稿按“替换通道并逐步接主 Agent 能力”组织；若范围收缩，验收和排期都应同步收缩。

  2. 应用归属：复用原 Bot 应用，还是使用 CLI 流程创建的新应用？

    要考虑已有用户绑定、用户标识、可见范围和迁移影响，不能只看凭据是否可拿到。

  3. 知识库范围：Bot 能访问哪些空间与文档？

    明确管理员、授权动作、撤销机制和测试空间；区分“没权限”与“没有内容”。

  4. 主 Agent 工具开放顺序：先读，还是先允许写？

    建议先以知识检索和文档读取验证价值，再逐域定义写操作与确认策略。

  5. 既有体验底线：哪些群聊、审批、附件和会话行为必须原样保留？

    评审应确认完整回归范围，不能仅验证能发一条文本消息。

  6. 多用户与多连接：是单企业、单应用试点，还是继续支持每用户连接？

    决定连接归属、状态管理、身份兼容和灰度对象，需在评审中明确。

  7. 失败与撤销：谁看到什么提示，谁能修复？

    缺应用权限、Bot 未加入空间、资源删除、断线重连应分别有可操作的反馈。

  8. 发布门槛：哪些真实企业链路通过后，才能替换旧通道？

    把“命令支持”与“线上可用”分开；未达到验收标准时保持评审状态。

验收目标：从“能调用”到“可交付”

用户价值验收

  • 知识问答可引用

    群内提问命中已授权知识库，回答含正确标题和可打开链接。

  • 权限边界可证明

    无权限、撤权和资源删除场景不返回旧正文，并给出正确反馈。

  • 主 Agent 工作可完成

    从用户消息到 Agent 处理、工具调用、回复形成完整闭环。

  • 原有协作不退化

    群聊、私聊、卡片、审批、附件、线程和会话连续性与旧通道对齐。

上线门槛

  • 真实应用配置已核对

    应用身份权限、机器人能力、事件配置、版本发布和资源授权不是截图推断。

  • 异常与稳定性已回归

    断线重连、重复事件、审批幂等、连接撤销和失败恢复均有验证。

  • 数据流与性能已验收

    知识库召回、分页、正文按需读取、限频和上下文边界有实测依据。

  • 灰度和回滚可执行

    有明确试点对象、切换条件和退出旧通道的标准；未通过则不切换。

建议的评审产出一页已确认的产品定义、一份决策清单、一组真实企业 UAT 场景。完成这些后，再输出技术蓝图、模块拆分、接口契约与实施排期。
