候选方案 · 本次评审

一个方案：CLI 的 Bot 身份替代现有 IM Feishu 连接

所有飞书消息入口和主 Agent 的飞书能力统一由 Bot 应用身份承接。用户在原群聊、私聊和卡片中继续工作，不感知底层通道切换。

  • 接入范围：整个现有 IM Feishu 连接；同时接主 Agent 的消息、知识库、文档、云盘、通讯录和任务等受权能力。
  • 产品收益：一套 Bot 身份、一个统一能力入口，知识库能自然成为主 Agent 的资料源。
  • 产品代价：必须确认原群聊、私聊、卡片、审批、附件和会话行为在替换后保持连续。
  • 适合：要把主 Agent 做成飞书内完整工作入口，并愿意做一次完整通道替换评审。
最小范围备选

保留现有 IM Feishu 连接，只新增知识库

现有 Bot 继续负责消息入口；另把知识库作为只读资料源接给主 Agent。通道不变，只扩资料范围。

  • 接入范围：只增加知识库与文档读取；不替换消息、卡片和审批链路。
  • 产品收益：改动面最小，P0 价值和验收边界最清楚，风险集中在权限与资料召回。
  • 产品代价：主 Agent 仍有多套飞书能力入口，统一 Bot 身份的收益无法一次到位。
  • 适合：领导层 P0 只想先让知识库可用，暂不接受通道替换风险。

技术评审与影响面

这里不写命令、模块、字段或实施排期，只列出评审方案时必须同时看到的能力与影响。具体技术蓝图等产品确认后再出。

替换什么

现有 IM Feishu 连接中的 Bot 消息入口，以及主 Agent 当前分散的飞书 API 调用能力。

接进来什么

同一个 Bot 应用身份下，被授权的消息、知识库、文档、云盘、通讯录、任务等 CLI 能力。

必须延续什么

用户连接、群绑定、会话连续性、卡片与审批、附件、权限边界、失败反馈和可回滚。

方案判断技术方向可评审为候选，但企业应用配置、资源授权、消息链路等价性、知识库召回与生产稳定性尚未真实验证。页面里所有结论都是产品意见，不代表已完成上线。
范围提醒Bot 身份不等于用户个人身份；全部权限不等于能访问所有私人资源。产品要确认的是应用可见范围、资源授权和写操作边界。
